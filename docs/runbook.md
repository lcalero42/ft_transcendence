# Runbook

Operational how-to for running, debugging, and fixing the stack locally.
For *why* things are structured this way, see [architecture.md](architecture.md).

## First-time setup

1. Create the required `.env` files:
   - `srcs/.env` — app config; must include `PROJECT_PATH=<absolute path to
     the repo>` (used by Compose for the bind-mount volumes).
   - `srcs/containers/back/project_volume/.env` — placeholder file checked
     by `make check-env`; the real values are regenerated by
     `entrypoint.sh` from Docker secrets on every container start, so this
     file just needs to exist and be non-empty.
   - `srcs/containers/front/front_data/.env` — **must live inside
     `front_data/`**, not `srcs/containers/front/.env`. Only `front_data/`
     is bind-mounted into the container as `/app`; a `.env` placed one
     level up is invisible to Vite and every `VITE_API_URL`-based fetch
     call silently resolves to `undefined/...` (see "Frontend can't reach
     the backend" below — this exact mistake has happened before).
     Minimal contents: `VITE_API_URL=http://localhost:3000`.
2. Create the Docker secrets (`make check-secrets` verifies these exist and
   are non-empty):
   ```
   srcs/secrets/db_user.txt
   srcs/secrets/db_password.txt
   srcs/secrets/db_name.txt
   srcs/secrets/jwt_secret.txt
   srcs/secrets/internal_api_key.txt
   ```
   Each file holds a single value, no trailing newline conventions
   enforced — just don't leave them empty.
3. `make buildd` — build and start everything, detached.

## Everyday commands

All commands run from the repo root; run `make help` for the full list.

```bash
make up / make upd      # start (attached / detached)
make down               # stop and remove containers
make re                 # down + up (keeps volumes, i.e. keeps DB data)
make re-front            # rebuild only the front container
make re-back             # rebuild only the back container
make logs / make logs-front / make logs-back
make ps                  # container status
```

## Database

- `postgres` has no host-published port — reach it only via the `back`
  container or `docker compose exec postgres psql ...`.
- Prisma Studio is auto-started by `back`'s entrypoint and reachable at
  `http://localhost:51212`.
- Migrations run automatically on every `back` container start
  (`prisma migrate deploy`), followed by `prisma generate` and
  `prisma db seed`.
- To create a new migration during development:
  ```bash
  make prisma-migrate     # runs `prisma migrate dev` inside back
  make prisma-generate    # regenerate the Prisma client only
  ```
- To fully reset the database, `make fclean` (asks for confirmation) removes
  named volumes including Postgres data, then `make buildd` reseeds from
  scratch.

## Checks (mirrors CI)

```bash
make check-lint        # eslint, front + back
make check-lint-fix    # eslint --fix, front + back
make check-typecheck   # tsc, front + back
make check-all         # all of the above, reports every failure instead of stopping at the first
```

These `exec` into the running containers, so `front`/`back` must already be
up (`make check-containers-up` verifies this and is a dependency of the
others).

## Troubleshooting

### Frontend can't reach the backend / pages show no data

Symptom: network requests to `localhost:3000/...` fail or resolve to a
literal `undefined/...` URL; UI looks like the database is empty or
disconnected even though `back` is healthy.

1. Confirm the env var actually reached the container:
   ```bash
   docker exec front cat /app/.env
   ```
   If this errors with "No such file or directory", the `.env` is sitting
   outside `front_data/` — move it to
   `srcs/containers/front/front_data/.env` and `make re-front`.
2. Confirm `VITE_API_URL` matches how you're accessing the app
   (`http://localhost:3000` for the default local setup).
3. Check CORS: `src/main.ts` in `back` only allows the origin
   `http://localhost:5173`. If you're accessing the front from a different
   host/port, requests will be blocked by the browser — update
   `enableCors` in `back`'s `main.ts`.

### `back` won't start / crashes on boot

- Check `make logs-back`. Most startup failures are `entrypoint.sh` failing
  to read a secret file (missing/empty file under `srcs/secrets/`) or
  `prisma migrate deploy` failing against a Postgres that isn't ready yet
  (the `depends_on: condition: service_healthy` should prevent this, but a
  stale/corrupt volume can still cause migration errors — try
  `make fclean && make buildd` as a last resort, it wipes DB data).

### `401 Unauthorized` on routes that used to work

- Most `player`, `room`, and `game` mutation routes require a JWT
  (`JwtAuthGuard`). Confirm the frontend is sending
  `Authorization: Bearer <token>` and that the token hasn't expired
  (`JWT_EXPIRES_IN`, default `1d`).
- `word-pair` writes require the internal API key header
  (`x-internal-api-key`), not a JWT — this endpoint is meant for
  service-to-service calls, not the browser.

### Changed the Prisma schema and nothing updates

- Regenerate the client and re-run migrations inside the container:
  `make prisma-migrate` (dev) or restart `back` to pick up
  `migrate deploy` on boot.
- `typecheck` for `back` runs `prisma generate` first
  (`npm run typecheck` = `prisma generate && tsc --noEmit`), so a stale
  generated client shouldn't cause false typecheck failures in CI — but it
  can locally if you're running `tsc` directly without that step.
